멀티드론 영상을 하나의 3D 장면으로 복원하는 파이프라인이다.
**결정과 그 근거**를 기록하는 단일 출처이며, 측정값은 [`RESULTS.md`](RESULTS.md),

상위 문서와의 관계는 [`../../CLAUDE.md`](../../CLAUDE.md)의 문서 지도를 따른다.
이 문서는 `docs/ARCHITECTURE.md`의 3-Tier 중 **Core HPC의 3DGS 복원 부분**을 구현한다.

> 지금 이 폴더의 코드는 cumulus3d 기반 라이브 복원 엔진(§0)이다.
> §1, §3 ~ §5의 3DGS 기록은 측정 근거로 남긴다.

## 0. 라이브 복원 엔진 (Rust)

COLMAP·gsplat 파이프라인은 `mod.rs`의 `Engine`으로 대체됐다.
`route_gen.py`(DJI 웨이포인트 KMZ 생성)는 촬영 계획 도구라 엔진이 쓰지 않아 옮기지 않았고,
`split_segments.py`·`align_scene.py`가 하던 구간 자르기와 좌표 맞추기는
cumulus3d의 구간(zone)과 GPS ENU 정렬이 대신한다.

```
FrameSet(gRPC) → Assembler(카메라 모으기) → LiveFrameSet → ReconNode.compose
  ├─ on_frame 훅 → 큐(최대 24장) → UNet → 관측(축소 확률 격자 + 사람 점)
  ├─ 파일 싱크(stable display) → <work_dir>/runs/live-<스트림 id>-<pid>/live/stream/
  │    └─ follower(slotstream.rs, 200 ms): 새 사건 → PBSD 머리 + 팩 → CHUNK_KIND_POINT_SLOTS
  └─ 이벤트 ZoneRefined (stable display에는 ZonePreview가 없다)
       ├─ 점: 조밀화가 없을 때만 pointblitz 청크 v2 (stable display를 끄면 미리보기·정제본 모두)
       ├─ 메시: deltamesh ingest(구간, Preview|Refined) → extract → 바뀐 블록만 MeshBlock
       └─ 탐지 융합: 등록 포즈로 투영 → 프레임 간 confidence 가중 → DetectionBatch
  → ChunkLog(sequence 부여, 재생 기록) → SubscribeChunks
```

| 항목 | 결정 |
|---|---|
| ENU 원점 | 모든 프레임 묶음 맨 앞에 `.skylens-anchor` GPS 기록(앵커 좌표)을 넣는다. cumulus3d는 첫 GPS 기록을 원점으로 고정하므로 모든 구간이 앵커 기준 ENU 미터(x 동, y 북, z 위)로 나온다 |
| 조정 정책 | append-only. 늦게 오거나 고쳐진 묶음은 무시한다. deltamesh 정제본은 구간당 한 번만 넣을 수 있고, 이미 내보낸 구간을 되감지 않기 위해서다 |
| 카메라가 따로 오는 묶음 | 같은 키의 push를 모아 모든 카메라가 차면 선언한다. 대기 중인 묶음은 최대 64개 |
| stable display | 기본(`SKYLENS_STABLE_DISPLAY=1`). 미리보기가 없고 구간 K의 정제는 K−1을 기다리며, GPS 위치 제약으로 한 번 보인 구간은 움직이지 않는다. 내부값이 안정되기 전(1 %, 늦어도 구간 3)에는 앞 구간을 다시 놓고 `ZoneRefined`를 다시 낸다 |
| 점 슬롯 | 노드에 실행 폴더를 주어 cumulus3d가 live diff stream v4를 쓰게 하고, follower가 사건마다 청크 하나로 낸다(`segment` 사건 구간, `version` 순번, `generation` 스트림 id). 스트림 id는 `runs/` 아래 가장 큰 id + 1과 시작 시각 초 중 큰 값이고, 청크 시퀀스는 `스트림 id << 32`에서 시작한다(다시 뜬 모델 서버의 청크가 코어의 이어받기 시점보다 모두 크다). 실행 폴더에는 run.log, 타임라인, 차분 스트림만 쓰고(`stream_only`), 시작할 때 실행 폴더를 3개(`KEEP_RUNS`)만 남긴다. 화면용 점은 1/6(`SKYLENS_LIVE_STRIDE`). 조밀화가 실패한 구간(`dense: false`)은 스트림에 없으므로 그 구간만 점 청크로 보낸다 |
| 메시와 재배치 | 구간 3까지는 다시 놓일 수 있어 deltamesh에 미리보기 수준으로 넣고(다시 오면 교체), 구간 4가 오면 그 구간들의 마지막 점을 정제 수준으로 넣는다. 점이 그대로면 메시가 바뀌지 않아 블록을 다시 보내지 않는다(그 블록 청크의 수준은 미리보기로 남는다). 구간이 4개 이하인 실행은 구간 0~3의 메시가 미리보기 수준으로 남는다 |
| 미리보기 좌표계 | (stable display를 끈 경우) 구간 0과, 정제본이 채택된 뒤의 미리보기만 GPS 정렬이다. 정렬되지 않은 미리보기는 내보내지 않고 정제본을 기다린다 |
| 조밀화 | CUDA가 필요하다. `gpu = false`면 구간 모델의 희소 점을 대신 쓴다 |
| 메시 GPU | `gpu-mesh` 기능을 켜고 빌드하면 `GpuMesher`, 아니면 CPU `SdfMesher` |
| `push` | 위치 하나를 처리하는 동안 막힌다. 비동기 서버에서는 blocking 스레드에서 부른다 |
| 청크 재생 | 블록은 최신 버전, 탐지는 구간별 최신 묶음, 점은 구간별 최신 세대만 남긴다. 점 슬롯은 합치지 않고 모두 남긴다 |

### 0.1 탐지 융합 (`fusion.rs`)

- 구간 점을 동·북 1 m 칸으로 묶고 칸 중심을 프레임마다 투영한다. 포즈는 구간 모델의 등록 포즈다.
  `FrameRegistered`의 포즈는 체인 좌표계라 정제본이 채택되기 전에는 ENU가 아닐 수 있어서 쓰지 않는다.
- 위험구역: 투영된 픽셀의 클래스 확률을 그 픽셀의 최대 확률로 가중해 더한다. 가중 평균에서 가장 높은
  클래스가 0.5 이상이고 2프레임 이상이 본 칸만 위험구역이다. 같은 클래스로 맞닿은 칸(8방향)이 한 구역이고,
  외곽선은 칸 모서리의 볼록 껍질이다.
- 사람: 사람 점을 가장 가까운 칸 투영에 붙이고 2 m 안의 기존 사람과 합친다. 그 위치를 볼 수 있었던 프레임은
  검출 여부와 관계없이 모두 센다. confidence는 점수 합을 본 프레임 수로 나눈 값이고,
  2프레임 이상 검출되고 0.4 이상일 때 보고한다. 한 프레임의 오검출은 지도에 찍히지 않는다.
- id는 갱신과 정제본 교체에도 유지된다. 겹치는 이전 구역, 2 m 안의 이전 사람의 id를 물려받는다.
- 가림은 따지지 않는다. 항공 시점에서는 칸 중심 투영으로 충분하다고 보고 단순화했다.
- UNet이 밀리면 오래된 프레임부터 버린다. 융합이 프레임 사이를 보간하므로 빠진 프레임은 프레임 수만 줄인다.

### 0.2 잡 API (`jobs.rs`, `sources.rs`)

- `steps`가 7,000 미만이면 미리보기, 이상이면 정제본이다. 옛 코어 사다리(1,000 / 7,000 / 30,000 스텝)에서
  7,000 스텝이 "실용 품질"이었던 것을 경계로 삼았다.
- `uri`는 로컬 경로다(`file://` 접두어 허용). 폴더면 안의 jpg·png, 이미지 파일이면 한 장,
  그 밖의 파일은 영상으로 보고 `ffmpeg`로 초당 2장을 뽑는다(`SKYLENS_FFMPEG`로 실행 파일 지정).
  소스 i가 카메라 i(left, center, right)다.
- 프레임의 GPS는 소스의 `poses`에서 같은 상대 위치를 고르고, 없으면 `track`을 보간한다.
- 잡마다 별도 노드를 띄워 구간 하나(`zones(위치 수, 0)`)로 돌린다. 위치는 최대 120개로 고르게 솎는다.
- 결과 PLY는 `<work_dir>/results/`에 쓰고 `url`은 `/results/<파일>`이다.
  좌표가 이미 앵커 기준 ENU라 `align`은 항등이고, `anchorFrame`은 앵커에서 만든 id다.
- 탐지 잡도 포즈와 표면이 필요하므로 미리보기 복원을 같이 돌리고 라이브와 같은 융합을 쓴다.

## 1. 이 파이프라인이 하는 일

영상 한 편이 3D 장면이 되기까지 두 단계를 지난다.

```
영상 → 프레임 추출 → COLMAP SfM → gsplat 학습 → .ply
        (ffmpeg)     (카메라 포즈)   (가우시안 최적화)
```

**앞단(COLMAP)** 은 각 프레임이 어디서 어느 방향을 보고 찍혔는지를 역산한다.
특징점을 찾고, 프레임 쌍끼리 대조해 같은 지점을 찾고, PnP·삼각측량·번들조정을
번갈아 돌려 카메라 포즈와 3D 점을 동시에 푼다.

**뒷단(gsplat)** 은 그 카메라 배치를 근거로 공간을 가우시안으로 채운다.

### 반드시 짚고 갈 것 — 이건 예측이 아니라 최적화다

3DGS는 학습된 모델이 형상을 추론하는 방식이 **아니다.**
장면마다 처음부터 수십만 개 가우시안의 위치·크기·방향·불투명도·색을
경사하강으로 맞춰 나간다. 따라서

- 새 장면마다 매번 처음부터 다시 돌려야 한다 (사전학습 가중치가 없다)
- **입력 영상에 없는 정보는 절대 생기지 않는다** — 안 찍힌 면은 안 나온다

발표에서 "AI가 3D를 만들어낸다"로 설명하면 심사에서 무너진다.
"여러 시점의 실측 영상으로부터 형상을 역산한다"가 정확한 표현이다.

### 이 레이어가 맡는 범위 — 현장의 정적 골격

3DGS 는 **움직이는 대상을 복원하지 않는다.** 그건 결함이 아니라
[`skylens_model/README.md §0`](../../README.md) 의 레이어 분리에서 나온 역할 배분이다.

| 레이어 | 맡는 것 |
|---|---|
| ① 탐지 (UNet) | 프레임 1장에서 사람·위험구역 |
| ② 투영 (레이캐스팅) | 그 결과를 3D 좌표로 |
| ③ 랜드마크 융합 | 3D 공간·시간 누적 |
| **3DGS** | **②가 쓸 depth 를 만드는 현장 기하** |

사람과 불꽃은 ①②③이 맡고, 3DGS 는 그 투영이 꽂힐 골격을 공급한다.
따라서 여기서 풀어야 하는 문제는 "3DGS 로 사람을 복원하기" 가 아니라
**"움직이는 대상이 정적 복원을 오염시키지 않게 하기"** 다.

## 2. 구조

```
src/skylens_model/models/skylens/
├─ README.md     # 이 문서. §0 라이브 엔진, §1 이후는 이전 3DGS 방식의 결정과 근거
├─ INSTALL.md    # (이전 방식) COLMAP·gsplat 설치, 밟았던 함정 10건
├─ RESULTS.md    # (이전 방식) 실험 5건 측정값 전체
├─ mod.rs        # Engine: 노드 선언, push, subscribe, 잡
├─ frames.rs     # FrameSet → LiveFrameSet, 카메라 모으기, 앵커 GPS 기록
├─ live.rs       # 탐지 워커, 이벤트 전달, 청크 소비자, 정제본 수거
├─ recon.rs      # cumulus3d 결과 → 점·카메라 뷰
├─ fusion.rs     # 탐지 투영과 프레임 간 융합 (순수 계산, 단위 테스트)
├─ chunks.rs     # 청크 인코딩, sequence, 재생 기록
├─ slotstream.rs # live diff stream follower → 점 슬롯 청크 (시험은 src/test/tests/slots.rs에서도 돈다)
├─ jobs.rs       # 잡 실행, steps → 수준
└─ sources.rs    # uri → 프레임 (폴더·이미지·ffmpeg)
```

이전 방식의 Python 도구(`colmap_io.py`, `ckpt_to_ply.py`, `subset_model.py`, `pose_noise.py`,
`route_gen.py` 등)와 `RESULTS.md` 를 만든 `scripts/` 는 지웠다. git 기록에 남아 있다.

산출물은 저장소 안에 두지 않는다. `.gitignore` 가 `data/` 와 `*.pt` 를 막고 있지만,
수 GB 짜리는 작업 트리 밖에 두는 편이 사고를 원천 차단한다.

## 3. 설계 결정과 근거

### 3.1 특징점은 ALIKED + LightGlue — SIFT를 쓰지 않는다

복도는 흰 벽과 균일한 바닥이 대부분이다. 사람이 설계한 SIFT는 이런 곳에서
특징점을 많이 잡지만 대부분 신뢰할 수 없어 매칭 단계에서 무더기로 걸러진다.

같은 540장에 대한 정면 비교 ([`RESULTS.md` 실험 1](RESULTS.md#실험-1--sift-vs-aliked)):

| | SIFT | ALIKED + LightGlue |
|---|---|---|
| 기하 검증 통과율 | 56% | **91%** |
| 등록 결과 | **3개 모델로 분열** (최대 399장) | 540/540 단일 모델 |
| 왜곡계수 k1 | +0.4482 (발산) | +0.0778 |
| 특징점 추출 | 1분 24초 | 35초 |
| 매퍼 | 1시간 7분 | 54분 |

가장 심각한 건 **왜곡계수 발산**이다. 잘못된 매칭이 많으면 자기보정 최적화가
물리적으로 말이 안 되는 값으로 굴러떨어진다. 속도를 포기하고 정확도를 산 게 아니라
**양쪽 다 이겼다.**

> 배제한 대안: SIFT + 순차매칭. 영상 한 편이면 쓸 만하지만 여러 촬영본을
> 하나로 합칠 때 촬영본 간 연결을 못 찾는다 (§3.2).

### 3.2 매칭은 전수매칭 — 순차매칭으로는 촬영본을 못 합친다

영상 한 편만 쓸 때는 프레임이 시간순이라 이웃끼리만 맞춰도 된다.
그런데 **여러 촬영본을 하나의 좌표계로 합치려면** 2037의 어느 프레임이
2039의 어느 프레임과 같은 곳을 보는지를 시간 단서 없이 찾아야 한다.

대가는 프레임 수의 제곱이다. 540장이면 145,530쌍이고,
360장 → 540장으로 1.5배 늘렸더니 매칭 시간이 **5배**가 됐다.
실시간 파이프라인의 첫 병목이 여기다.

### 3.3 내부 파라미터는 명시하고 자기보정은 켠다

`--ImageReader.camera_params`로 초점거리를 주고,
`--Mapper.ba_refine_focal_length 1`로 보정도 허용한다.

둘 중 하나만 하면 실패한다. 파라미터 없이 보정을 끄면 COLMAP이 기본값
(가로폭의 1.2배)에 고정하는데, 실측 대비 **46% 과대**였다.
파라미터 없이 보정만 켜면 위 §3.1의 발산이 일어난다.

### 3.4 중간 체크포인트를 계속 뽑는다

품질 곡선이 로그 형태라 **초반에 대부분을 벌어들인다**
([`RESULTS.md` 실험 2](RESULTS.md#실험-2--점진적-출력)).

```
   250 →  1,000 스텝:  +2.38 dB
10,000 → 30,000 스텝:  +1.60 dB   (스텝은 20배인데 이득은 절반)
```

전체의 3%인 1,000스텝 시점에 최종과 5.15dB 차이까지 좁혀진다.
회의에서 재정의한 **"30초는 완성 시간이 아니라 갱신 주기"** 구조가
실제로 성립한다는 근거다. 첫 화면은 낮은 스텝으로 띄우고 계속 개선하면 된다.

가우시안 증식은 15,000스텝에서 멈춘다. 이후로는 **파일 크기가 고정**되고
기존 가우시안을 다듬기만 한다 — KOREN 전송량 산정에 필요한 사실이다.

### 3.5 PLY 경량판을 따로 뽑는다

3DGS의 `.ply`는 컨테이너만 PLY이고 내용은 포인트 클라우드가 아니다.
원소 하나당 59개 속성을 가진다 (포인트 클라우드는 6개).

```
x, y, z              위치                     3
f_dc_0..2            기본 색                  3
f_rest_0..44         보는 각도별 색 변화(SH)  45   ← 경량판에서 제거
opacity              불투명도                 1
scale_0..2           세 축 크기               3
rot_0..3             방향 쿼터니언            4
```

`f_rest` 45개를 빼면 **용량이 4분의 1**이 되고 형상은 그대로다.
각도에 따른 색 변화만 잃는다. 네트워크를 건너는 용도라면 경량판이 맞다.

`scale`과 `rot` 때문에 가우시안은 점이 아니라 **찌그러진 타원체**다.
벽에 붙은 가우시안은 벽면을 따라 납작하게 눌려 펴지면서 면을 이룬다.
CloudCompare나 MeshLab은 앞 세 속성만 읽고 나머지를 버려서 점으로만 보이는데,
**파일이 잘못된 게 아니라 뷰어가 3DGS를 모르는 것이다.**

## 4. 촬영 가이드 — 실험에서 나온 요구사항

### 4.1 포즈 정확도: 위치가 각도보다 훨씬 예민하다

([`RESULTS.md` 실험 3](RESULTS.md#실험-3--포즈-정확도-민감도))

```
자세 0.1°  −0.08 dB      위치 0.2%  −2.24 dB
자세 1.0°  −2.70 dB      위치 0.5%  −3.60 dB
```

위치 0.2%의 손해를 자세 오차로 내려면 **0.8° 가까이** 틀어야 한다.
카메라가 돌면 장면 전체가 같이 밀려 보정 여지가 있지만,
카메라가 옮겨지면 가까운 물체와 먼 물체가 다르게 어긋나 삼각측량 자체가 깨진다.

**실무적 결론**: GPS 수평 오차는 0.5~1.5m로 이 규모를 훨씬 웃돈다.
**드론 위치 텔레메트리를 3DGS 카메라 포즈로 직접 쓸 수 없다.**
포즈는 영상에서 다시 풀어야 한다.

### 4.2 편대 배치

현재 촬영본의 실측 기하 (의도와 다른 부분):

| 항목 | 의도 | 실측 |
|---|---|---|
| 편대 형태 | 정삼각형 | 변 길이 비 **2.0~7.8배** |
| 카메라 시선 | 아래를 내려다봄 | **−2.3° / +14.3° / +1.7°** (거의 수평) |
| 경로 간격 | 고르게 벌어짐 | 2038↔2039가 **0.144까지 근접** |

2039 프레임의 65%가 2038 경로 0.2 이내를 지난다.
2038에만 등장한 사람이 2039 시점에 잔상으로 남는 원인이다.

**다음 촬영에 반영할 것**: 횡방향 간격을 확실히 벌리고, 시선을 아래로 내려
겹치지 않는 바닥면을 각자 담당하게 한다. 경로가 붙으면 장수만 늘고
시차는 안 늘어나 오히려 손해다. 정삼각형 유지보다
**서로 다른 각도에서 같은 지점을 보는 것**이 핵심이다.

### 4.3 드론 자동 비행 — 현재 기종으로 가능한 범위

촬영 기종은 영상 메타데이터의 인코더 태그 기준 **DJI Lito X1**이다.

| 경로 | 가능 | 비고 |
|---|---|---|
| Mobile SDK v5 직접 제어 | ✗ | 지원 목록은 Mini 3/3 Pro/4 Pro와 기업용뿐 |
| DJI Fly 웨이포인트 (KMZ/WPML) | ✓ | 좌표·고도·기수·**짐벌 피치**·촬영 동작 지정 가능 |
| Litchi · Dronelink | ✗ | DJI가 SDK에 추가해야 대응 (2026-05 기준 미지원) |
| 실내 자동 비행 | ✗ | 웨이포인트는 위성항법 기반. 실내는 수동만 |

웨이포인트 KMZ를 프로그램으로 생성하는 방식이 현실적이다.
단 그 가치는 정확한 포즈 제공이 아니라 (§4.1에서 봤듯 GPS 정밀도로는 어림없다)
**좋은 촬영 배치를 매번 똑같이 재현**하는 데 있다.
`route_gen.py` 가 정삼각형 세 꼭짓점에서 출발하는 평행 직선 경로 3개를 KMZ 로 뽑는다
(엔진 전환 때 지웠고 git 기록에 남아 있다).
한 대뿐이므로 한 번에 한 leg 씩, 세 번 나눠 난다.

기종 enum 값은 **문서로 알 수 없다.** DJI 가 공개한 WPML 명세는 기업용 5기종
(M350/M300/M30/M3E/M3D)만 다루고 소비자 기종은 하나도 없으며, 대상 앱도
DJI Pilot 2 / FlightHub 2 뿐이다. 그래서 `--from-existing` 으로 **앱이 만든 경로에서
`droneEnumValue` 를 복사**해야 한다. 같은 이유로 생성한 KMZ 는 실제로 불러오기 전까지
검증되지 않은 것으로 취급한다.

### 4.4 실내는 수동뿐 — 편차를 줄이는 설정

웨이포인트는 위성항법 기반이라 실내에서는 모드 자체가 활성화되지 않는다.
복도 촬영은 수동이고, 재현성은 사람이 만들어야 한다.

| 설정 | 값 | 무엇을 잡는가 |
|---|---|---|
| 비행 모드 | **Cine** | 속도와 스틱 반응을 낮춰 좁은 공간 미세 조정 |
| Cruise Control | **켬** | 스틱을 놓아도 속도·방향 유지 → 등속 직선, 흔들림 제거 |
| 짐벌 피치 | **고정** | 실측 −2.3 / +14.3 / +1.7° 의 편차 제거 |
| 기수 | 경로 방향 | 축 하나만 써서 대각선 조작을 없앰 |
| 바닥 표식 | 시작점 3개 + 진행선 | 삼각형 변 비율 고정 |

녹화는 직선 구간에서만 한다. 시작점까지의 이동은 녹화하지 않으므로
대각선으로 움직여도 상관없다.

> Hyperlapse 의 Course Lock 은 쓰지 않는다. 타임랩스라 프레임을 띄엄띄엄 찍는데,
> 3DGS 는 연속 프레임의 중첩이 필요하다.

## 5. 증분(누적) 복원 — 가능하다

`docs` 회의록(2026-08-07)의 3DGS 담당 액션 아이템에 대한 답이다.
회의록에는 *"누적 복원이 불가능한 것으로 판명되면 가우시안 스플래팅 자체를
재설계해야 함"* 이라는 우려가 적혀 있었다. **그 우려는 해소됐다.**

이전 결과를 초기값으로 이어 학습(웜스타트)했더니 처음부터 학습하는 것보다
6.5dB 나빴다 ([`RESULTS.md` 실험 5](RESULTS.md#실험-5--증분-학습)).
원인은 알고리즘이 아니라 **좌표계**였다.

gsplat의 데이터 로더는 `normalize=True`일 때 **카메라 집합으로부터 좌표 변환을
계산**한다. 장면을 원점 근처로 옮기고 크기를 맞추는 정규화인데,
카메라가 늘면 그 변환도 새로 계산된다.
75장 기준 변환과 150장 기준 변환이 **87.8° 틀어져** 있었다.
이전 단계에서 맞춰 놓은 가우시안이 통째로 회전된 공간에 떨어진 것이다.

**해결**: 첫 배치에서 계산한 정규화 변환을 저장해 이후 모든 배치에 강제한다.
3DGS 재설계가 아니라 데이터 로더 한 곳을 고정하는 문제다. 구현 대기.
