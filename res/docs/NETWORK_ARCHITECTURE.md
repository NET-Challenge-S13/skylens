## 1. KOREN이 실제로 주는 것

아키텍처는 쓸 수 있는 자원의 모양을 따라간다. 자원 신청 양식의 카탈로그와 HPC 이노베이션 허브 사용자 가이드에서 확인한 사양은 다음과 같다.

### 1.1 자원 카탈로그

| 자원 | 사양 · 위치 | 우리 용도 | 상태 |
|---|---|---|---|
| **접속 확인된 VM** (HPC 포털·판교로 추정) | Xeon Gold 6140 16c · V100 16GB · RAM 161GB (nvidia-smi 실측) | 연산 평면 — 3DGS 복원, AI 추론 | 확보 |
| **KOREN VM (대전)** | 사양 미확인 (NOC 안내 IP만 수령) | 제어 평면 — 수신·분할·잡 발행·계측 | 미개통 |
| AI Cloud GPU | H200 | 3DGS 학습 가속 (V100 대비 유리) | 미배정 |
| AI Cloud POD | CPU 컴퓨팅 자원 | 경량 서비스 분산 배치 후보 | 미신청 |
| vGPU T4 옵션 | T4 4GB · 8–40core | 탐지 워커 분리 배치 후보 | 검토 |
| 이음 특화망 5G-A | 판교 AI Network Lab | 액세스망 자체를 KOREN 직결로 대체 | 보류 (판교 전용, 상시 구성엔 불필요) |
| KOREN 백본 | 10Gbps 이상 · 전국 10개 PoP (상한은 출처별 상이) | 대전 ↔ 판교 구간 | 가용 |
| InfiniBand | 56G IB (VM 옵션, 가이드 표에서 재구성 — 확인 필요) | Core 내부 프레임·모델 전송 | 미확인 |

### 1.2 놓치고 있던 것 — 회선을 설계해서 요청할 수 있다

자원 신청 양식의 **2번 지식지원** 항목은 컴퓨팅 자원이 아니라 **네트워크 자체**를 요청하는 칸이다. 여기가 KOREN을 상용 클라우드와 구별짓는 지점이고, 초기 설계는 이 칸을 비워 둔 채 KOREN을 "GPU 달린 클라우드"로만 쓰고 있었다.

| 지원 서비스 | 무엇을 할 수 있나 | 우리 활용 |
|---|---|---|
| 전용회선 (L2) | 지점 간 레이어2 전용 경로 · VLAN 번호 지정 | 브리지 ↔ Core 결정론적 경로 |
| 전용회선 (λ) | 파장 단위 광 전용 회선 | Core 내부 대용량 구간 |
| E2E | POTN 기반 종단 간 서비스 · 사설 IP 대역 지정 | 전 구간 단일 관리 도메인 |
| NFV | 네트워크 기능 가상화 | 릴레이·트랜스코더를 VNF로 |
| BGP | 라우팅 정책 제어 | 규모상 과함 — 미사용 |
| 기술시연 · 시험환경 구성 | 실증 환경 구축 지원 | 최종평가 시연 |

**이것이 바꾸는 것**: 상용 클라우드는 리전 간 통신 경로를 사용자가 지정할 수 없다. 트래픽은 공용 백본을 타고, 지연은 best-effort이며, 다른 테넌트와 경합한다. KOREN은 VLAN을 찍어 전용 경로를 받을 수 있다. "안정적 QoS가 재난 미션 크리티컬 데이터 흐름에 필수"라는 주장은 L2 전용회선을 신청하면 실제 구현이 된다.

**설계에 직접 영향을 준 두 가지**
- 배정 GPU가 V100으로 확정됐다. H200 대비 3DGS 학습이 느리므로 30초 주기 예산에서 복원 잡의 여유가 줄어든다. iteration 축소로 15초 안에 들어오는지가 전체 성립을 쥔 유일한 미검증 항목이다.
- 자원이 종류별로 나뉘어 제공된다. V100·T4·CPU POD가 별도 신청 단위라는 사실이 서비스 분해의 근거가 된다. 무거운 복원과 가벼운 탐지를 같은 노드에 묶을 이유가 없다.

### 1.3 자원 정체 — 두 개인가 하나인가

신청은 HPC V100(판교)과 KOREN VM(대전) 둘 다 했는데, 현재 접속되는 것은 하나뿐이다. 두 주소의 성격이 달라 별개 자원으로 판단한다.

| 구분 | HPC 포털의 VM | NOC 안내 주소 |
|---|---|---|
| 주소 | 내부 10.246.246.9 / egress 116.89.174.50 | 116.89.187.181 |
| 사양 | V100 16GB · 16core · 161GB | 미확인 |
| 접속 | Horizon 콘솔 진입 성공 | 미개통 (refused) |
| 추정 역할 | **연산 평면** (판교 HPC) | **제어 평면** (대전 VM) |

근거는 두 가지다. egress 대역(`116.89.174.x`)과 안내 주소(`116.89.187.x`)의 `/24`가 다르고, VM에는 이미 sshd가 22번에 떠 있는데도 `116.89.187.181:22`는 여전히 거절된다. 같은 기계라면 통과했어야 한다.

> **[2026-08-15 갱신] 확정됨** — 이후 SSH 실측(포트 26022, `116.89.187.181` = 호스트명 `mnd`)으로 대전 VM이 별도 실체임이 확인됐다. **2노드 구성이 맞다.** 다만 대전 → 판교(10.246.246.9) 내부 라우팅은 ping/traceroute 모두 실패(KOREN 백본 2홉까지만 도달) — 별도 신청 필요 여부를 NOC에 재문의 중이다.

## 2. KOREN 활용 스택

경로의 각 구간마다 어떤 KOREN 자원이 그 구간을 책임지는지 대응시킨 것이 이 설계의 뼈대다. 일반적인 클라우드 MSA는 서비스가 한 데이터센터 안에서 돌고 그 사이 네트워크는 주어진 것으로 취급한다. 이 설계는 반대다 — **서비스를 전국에 흩어 놓고, 그 사이를 잇는 네트워크를 직접 설계한다.**

### 2.1 구간별 대응 자원

```
데이터 경로:   드론→GW  →  액세스 업링크  →  KOREN 진입  →  Core 내부  →  배포  →  단말
전송 계층:                  [이음 5G-A]      [——— E2E 전용회선(L2)·VLAN 지정 ———]  [다중 PoP]
컴퓨트 계층:                                  [KOREN VM]     [V100·T4·POD]
패브릭 계층:                                                 [56G InfiniBand]
보안 계층:                                    [——————— 양자암호 테스트베드 ———————]
검증 계층:      [차폐실(판교)]
```

### 2.2 계층별 활용 명세

| 계층 | KOREN 자원 | 해결하는 문제 | 상용 클라우드로 가능한가 | 단계 |
|---|---|---|---|---|
| 액세스 | 이음 특화망 5G-A | 업링크 병목 자체를 제거 · 등록 IP 문제 소멸 | 불가 | C |
| 진입 경로 | E2E 전용회선(L2) + VLAN | 경합·지터 제거, 결정론적 지연 | 불가 | B |
| 백본 | 10Gbps급 전국 백본 | 30초 주기 모델 버스트를 수백 ms에 전달 | 제한적 | A |
| 내부 패브릭 | 56G InfiniBand | Core 노드 간 프레임·모델 왕복 | 고가 옵션 | B |
| 연산(무거움) | HPC V100 16GB | 3DGS 증분 복원 | 가능 | A |
| 연산(경량) | vGPU T4 4GB | 탐지 추론 — 복원과 GPU 경합 회피 | 가능 | B |
| 제어 | KOREN VM · AI Cloud POD | 제어 평면 서비스 수용 | 가능 | A |
| 배포 | 다중 PoP (10개 거점) | 실증 지역 인근 분산 서빙 | CDN으로 유사 | B |
| 보안 | 양자암호 테스트베드 | 실종자 위치정보 구간 보호 | 불가 | C |
| 검증 | 차폐실(판교) | 무선 링크 기준선 측정 — 대조 실험 통제 | 불가 | C |
| 배포 확장 | Multicast | Edge 수와 무관한 배포 대역 | ISP 차단 | B |
| 우선순위 | QoS (DSCP) | 영상 트래픽 우선 처리 | 제한적 | B |
| 주소 | IPv6 | CGNAT 회피 — 등록 IP 문제의 다른 해법 | 가능하나 무의미 | B |
| 경로 제어 | MPLS · Light-Path | 트래픽 엔지니어링, 광 경로 | 불가 | C |
| 네트워크 기능 | NFV | 릴레이·트랜스코더를 VNF로 배포 | 제한적 | C |
| 실증 거점 | 공개시험센터 10개 지역 | 대전 거점 활용 — 충남대 인근 | 불가 | B |

**발표에서 쓸 한 문장**: 이 표에서 "상용 클라우드로 불가"인 항목이 곧 KOREN을 써야 하는 이유다. 액세스망 직결, 전용 경로 지정, 양자암호, 간섭 통제 환경 — 이 넷은 돈을 더 낸다고 살 수 있는 것이 아니라 연구시험망에만 있다.

### 2.3 단계별 확보 계획

| 단계 | 내용 | 시점 | 선행 조건 |
|---|---|---|---|
| A | HPC V100 · KOREN VM · 백본 — 기본 파이프라인 성립 | 확보 완료 | SSH 개통 |
| B | **L2 전용회선 + VLAN** · T4 추가 · 다중 PoP Edge · IB | 중간평가~최종평가 | 지식지원 신청서 제출 |
| C | 이음 5G-A · 양자암호 · 차폐실 · NFV | 최종평가 시연 | NOC 협의 · 판교 방문 |

B단계의 L2 전용회선이 가장 값이 크다. 신청 한 번으로 확보되고, 대조군(상용 인터넷 best-effort)과 정면으로 대비되며, 측정 지표(지터·지연 분포)로 차이를 증명할 수 있다.

## 3. 네트워크 구성 최종본

핵심은 **브리지가 관문과 배포를 겸한다**는 점이다. KOREN이 폐쇄망이라 사용자 대면 서빙을 망 안에서 할 수 없으므로, 등록 IP를 가진 망외 노드 하나가 들어가는 문과 나오는 문을 동시에 맡는다. 그 결과 데이터는 직선이 아니라 브리지를 축으로 되돌아 나오는 고리를 그린다.

```
드론×3 ─(제조사 무선링크)→ 현장 게이트웨이 ─(상용5G, SRT 15–33Mbps)→ ┐
                                                                      │
                                        ┌────────── 브리지 (등록 IP) ◄┘
                                        │  ① 관문 — SRT 릴레이
                                        │  ② 배포 — .spz 서빙
                                        │  ③ 캐시 — 복원본 보관
                                        └──────┬───────────────▲──────
                                     (KOREN)   ▼               │ 30초마다 .spz
                              ┌─ KOREN 폐쇄망 ─────────────────┴──┐
                              │  대전 VM(제어) ⇄ 백본 ⇄ 판교HPC(연산) │
                              └────────────────────────────────────┘
                                        │
                                        ▼ (HTTPS/WSS, 443 단일 포트)
                              상황판 · 대원 단말 (브라우저 3D 뷰어)

폴백: 게이트웨이 → (WiFi AP 직접) → 대원 단말   [백홀 단절 시]
```

### 3.1 왜 브리지가 필요한가

KOREN 자원 신청 양식에 명시된 보안 정책은 **사전 등록된 공인 IP 외 접속 불가**다. 사용자 단말은 상용 5G의 유동 IP를 쓰므로 등록할 주소 자체가 존재하지 않는다. 따라서 뷰어를 KOREN 안에서 서빙하는 구성은 정책상 성립할 수 없고, 등록 IP를 가진 망외 노드가 배포를 맡아야 한다.

방향에 따라 통제가 비대칭이라는 점이 설계의 자유도를 만든다. 실측 결과 **나가는 방향(egress)은 열려 있고 들어오는 방향(ingress)만 등록 IP로 제한**된다. 덕분에 결과물 전달은 두 방향 모두로 구성할 수 있어, 방화벽 승인 여부와 무관하게 파이프라인이 성립한다.

| 결과물 전달 방식 | 연결을 여는 쪽 | 필요한 방화벽 | 가용성 |
|---|---|---|---|
| Plan A — Core가 브리지로 push | KOREN VM → 브리지 | egress 443 | 확인됨 |
| Plan B — 브리지가 Core에서 pull | 브리지 → KOREN VM | inbound 22 (기신청) | 신청 완료 |

## 4. 서비스 분해 (MSA)

단일 프로세스로 묶으면 안 되는 이유가 이 시스템에는 구조적으로 존재한다. **복원과 탐지는 주기가 다르다.** 3DGS 복원은 10초 분량 프레임을 모아 30초마다 도는 배치 작업이고, 실종자 탐지는 프레임이 들어오는 대로 계속 도는 스트림 작업이다. 한 프로세스에 묶으면 무거운 복원이 도는 동안 탐지가 멈추고, 재난 상황에서 사람을 늦게 찾게 된다.

### 4.1 두 개의 독립 루프

```
ingest(MediaMTX, SRT수신)
  ├─→ [복원 루프 — 30초 주기 배치]
  │     segmenter(10초 프레임 묶음) → pose-sync(MAVLink 정합, SfM 생략 근거)
  │       → recon-worker(gsplat·V100, 목표 10–15초) ─┐
  │                                                    │(점선: 깊이 참조, 비동기)
  └─→ [탐지 루프 — 프레임 단위 연속]                    ▼
        detect-worker(TransUNet, RGB+열화상) → project(Depth 레이캐스팅, 2D→3D)
                                                          → event-hub(WSS push, 발견 즉시)

  recon-worker, project 둘 다 → asset(.spz+마커) → 브리지
```

두 루프는 서로를 기다리지 않는다. 복원이 15초를 쓰는 동안에도 탐지는 계속 돌고, 발견 즉시 마커가 나간다. 유일한 결합은 점선 하나 — 탐지 결과를 3D 좌표로 바꿀 때 복원된 장면을 깊이 참조로 쓰는 지점이며, 이 의존은 비동기라 탐지를 막지 않는다.

### 4.2 서비스 목록

**T1 · 현장 게이트웨이** (망외 · 노트북 + 5G 라우터)

| 서비스 | 설명 | 스택 |
|---|---|---|
| gw-encoder | 드론 영상 수신 후 H.265 트랜스코딩. 링크 상태에 따라 4K↔1080p 적응 조절 | GStreamer/FFmpeg |
| gw-pose | MAVLink 텔레메트리를 영상 타임스탬프에 결합. 이 포즈가 있어야 SfM을 건너뛴다 | MAVLink · NTP/GPS |
| gw-cache | 4K 원본 로컬 녹화, 최신 복원본 캐시. 백홀 끊기면 WiFi AP로 직접 서빙 | 로컬 스토리지 |

**T2 · 브리지** (등록 IP · 망외 ↔ KOREN 듀얼홈)

| 서비스 | 설명 | 스택 |
|---|---|---|
| bridge-relay | 현장에서 온 SRT 스트림을 KOREN 안으로 중계. 재인코딩 없이 통과 | SRT · UDP 8890 |
| edge-serving | TLS 종단, .spz 정적 서빙, WSS 리버스 프록시. 단말이 보는 모든 것을 443 하나로 수렴 | nginx |
| asset-cache | Core가 보낸 복원본 보관. 단말 요청은 여기서 받아 KOREN을 건드리지 않는다 | 파일 캐시 |

**T3 · 제어 평면** (KOREN VM 대전 · GPU 사용 없음)

| 서비스 | 설명 | 스택 |
|---|---|---|
| ingest | SRT/RTSP 스트림 수신. 미디어 경로에 nginx를 두지 않는 이유는 UDP를 프록시할 수 없기 때문 | MediaMTX |
| segmenter | 연속 스트림을 10초 분량 프레임 묶음으로 잘라 잡 1회분을 만든다 | 내부 서비스 |
| pose-sync | 프레임 묶음에 대응하는 포즈를 정합해 복원 입력을 완성 | 내부 서비스 |
| orchestrator | 30초 주기 복원 잡과 연속 탐지 잡을 각각 발행. 실행은 전부 판교 | FastAPI |
| queue | 잡 큐와 이벤트 버스. 서비스 간 결합을 끊어 부분 장애가 전파되지 않게 한다 | Redis Streams |
| metrics | SRT 통계, 잡 소요시간, 배포 지연 수집. 대조 실험 데이터의 절반이 여기서 나온다 | 계측 전용 (OpenTelemetry) |

**T4 · 연산 평면** (HPC 판교 · V100 16GB)

| 서비스 | 설명 | 스택 |
|---|---|---|
| recon-worker | 3DGS 증분 복원. 포즈 선공급으로 SfM 생략. 30초 예산의 최대 리스크 항목 | gsplat · GPU |
| detect-worker | RGB+열화상 4채널 입력으로 실종자·위험구역 탐지. 30초 주기에 묶이지 않는다 | TransUNet · GPU |
| project | 탐지 좌표를 복원 장면의 깊이 맵으로 역참조해 3D 마커로 변환 | Depth 레이캐스팅 |
| asset-store | 복원본과 마커를 버전 단위로 보관하고 브리지 전달을 트리거 | 오브젝트 스토리지(MinIO) |

### 4.3 이 분해가 정당한 이유

1. **주기가 다른 작업의 분리.** 복원은 배치, 탐지는 스트림이다. 묶으면 서로를 막는다.
2. **자원 요구가 다른 작업의 분리.** 복원은 GPU 메모리 집약, 탐지는 처리량 집약, 인제스트는 I/O 집약이다. KOREN이 V100·T4·CPU POD를 별도 단위로 제공하므로 요구에 맞춰 배치할 수 있다.
3. **장애 격리.** 탐지가 죽어도 복원은 계속되고, 복원이 밀려도 마커는 나간다. 재난 대응 시스템에서 부분 실패가 전체 실패가 되면 안 된다.
4. **대조 실험의 배포 단위.** 같은 코드를 KOREN과 상용 클라우드 양쪽에 올려 비교해야 하므로, 서비스 경계가 곧 배포 경계가 된다.

### 4.4 지리 분산 MSA — 이 구조가 특이한 지점

일반적인 MSA는 서비스가 한 데이터센터 또는 한 VPC 안에서 돌고, 서비스 간 네트워크는 *주어진 것*으로 취급한다. 이 설계는 서비스를 전국에 흩어 놓고 그 사이를 잇는 경로를 직접 설계한다.

| 구분 | 일반 클라우드 MSA | 이 설계 |
|---|---|---|
| 서비스 위치 | 단일 리전 · 단일 VPC | 현장 · 브리지 · 대전 · 판교 · PoP |
| 서비스 간 경로 | 제공사 내부망 (제어 불가) | KOREN 백본 · L2 전용회선 (지정 가능) |
| 지연 특성 | best-effort, 테넌트 경합 | 전용 경로 시 결정론적 |
| 네트워크의 지위 | 인프라 (블랙박스) | 아키텍처의 일부 (설계 대상) |

**서비스 메시의 데이터 플레인이 전국 전용망 위에 올라간다**는 것이 이 아키텍처의 한 줄 요약이다. 그래서 서비스 경계를 어디에 긋느냐가 곧 어느 구간에 전용회선을 신청할지를 결정한다 — 소프트웨어 설계와 네트워크 설계가 같은 결정이 된다.

### 4.5 서비스 간 통신 규약

동기 호출을 최소화하고 큐를 통한 비동기 전달을 기본으로 한다. 복원 잡이 15초를 쓰는 동안 호출자가 붙잡혀 있으면 안 되고, 판교 노드가 잠시 끊겨도 대전에서 잡이 쌓여 있다가 재개돼야 하기 때문이다.

| 구간 | 방식 | 메시지 · 페이로드 | 실패 시 |
|---|---|---|---|
| ingest → segmenter | 내부 스트림 | 프레임 + 수신 타임스탬프 | 버퍼 드롭, 다음 세그먼트로 |
| segmenter → queue | 비동기 발행 | `recon.job` — 세그먼트 ID, 프레임 경로, 포즈 | 큐에 적재, 워커 복귀 시 소비 |
| queue → recon-worker | 비동기 소비 | 잡 티켓 1건 | 미확인 잡은 타임아웃 후 재큐 |
| recon-worker → asset-store | 쓰기 | `scene.v{n}` — .spz + 메타 | 이전 버전 유지, 다음 주기 재시도 |
| detect-worker → event-bus | 이벤트 발행 | `marker.found` — 좌표, 신뢰도, 클래스 | 독립 채널, 복원 상태와 무관 |
| event-bus → 단말 | WSS push | 마커 이벤트 | 재연결 시 최근 이벤트 재전송 |
| orchestrator → 워커 | 동기 (상태 조회만) | 헬스체크, 잡 상태 | 회로 차단 후 해당 워커 제외 |

> **참고 — Redis(Message Queue)에 실제로 들어가는 것**: 영상 프레임이나 복원 파일 같은 무거운 데이터가 아니라, "세그먼트 47번 준비됨, 저장 위치 xxx" 같은 몇 KB짜리 티켓/이벤트뿐이다. 무거운 데이터는 오브젝트 스토리지(MinIO)나 직접 전송으로 별도 이동한다.

### 4.6 MSA 패턴 적용

| 패턴 | 이 시스템에서의 구현 | 왜 필요한가 |
|---|---|---|
| API Gateway | 브리지 nginx — 443 단일 진입점 | 단말이 내부 서비스 위치를 알 필요 없음. 폐쇄망 경계와도 일치 |
| 이벤트 드리븐 | Redis Streams — 잡 큐 + 이벤트 버스 | 복원 지연이 탐지를 막지 않게 하는 유일한 방법 |
| 읽기·쓰기 경로 분리 | 복원 파이프라인 ↔ 뷰어 서빙 | 단말 요청이 KOREN 안까지 들어오지 않음 |
| 회로 차단 | 워커 헬스체크 실패 시 잡 발행 중단 | 죽은 워커에 잡이 쌓여 큐가 막히는 것 방지 |
| 보상 처리 | 복원 실패 시 이전 `scene.v{n-1}` 유지 | 화면이 비는 것보다 30초 전 장면이 낫다 |
| 독립 스케일링 | 워커별 인스턴스 수 개별 조정 | 드론이 늘면 탐지만, 장면이 커지면 복원만 증설 |
| 분산 트레이싱 | 프레임 타임코드를 전 구간 전파 | 과제 산출물 그 자체 |

**관측 가능성이 부가 기능이 아닌 이유**: 이 과제의 결과물은 3D 상황판만이 아니라 KOREN과 상용망의 정량 비교 데이터다. 촬영 시점의 타임코드가 프레임에 박혀 세그먼트 → 잡 → 복원본 메타데이터 → 뷰어까지 전파돼야 E2E 지연을 실측할 수 있다. 서비스 경계마다 계측점이 자연히 생긴다는 점이 MSA를 택하는 또 하나의 실질적 이유다. 모놀리스였다면 구간별 분해가 불가능해 "느리다"는 말밖에 못 한다.

### 4.7 전체 구성도 (층으로 본 구성)

```
[클라이언트] 관제탑 상황판(Three.js) · 현장 대원 뷰어(모바일)
      ▲
      │ HTTPS/WSS
[브리지 — 175.126.98.44]  bridge-relay(SRT) · API Gateway(nginx,443) · asset-cache(.spz)
      ▲(SRT UDP8890, WSS443)          │
      │                                ▼
[제어 평면 — KOREN VM 대전]  ingest · segmenter · pose-sync · api-core
                              orchestrator · event-hub · metrics(OTel)
      ═══════════════ 메시지 버스 — Redis Streams ═══════════════
      (잡 큐 recon.job/detect.job + 이벤트 버스 marker.found/scene.updated)
      │                                ▲
      ▼                                │
[연산 평면 — HPC 판교 V100, PBS Torque]  recon-worker(gsplat) · detect-worker(TransUNet)
                                        project-worker(Depth 레이캐스팅)
      │
      ▼
[데이터 계층] PostgreSQL+PostGIS(미션·세션) · Redis(큐·캐시) · MinIO(.spz·프레임) · TimescaleDB(계측)
```

서비스는 버스를 통해서만 서로를 안다 — 직접 호출은 헬스체크뿐. 그래서 워커를 다른 자원으로 옮겨도 나머지가 바뀌지 않는다. **버스가 제어 평면과 연산 평면을 잇는 유일한 통로이며, 두 평면이 서로 다른 KOREN 자원(대전 VM/판교 HPC) 위에서 돌기 때문에 버스를 지나는 트래픽이 곧 KOREN 백본을 타는 트래픽이 된다.**

### 4.8 독립 스케일링 시나리오

| 상황 | 증설 대상 | 건드리지 않는 것 |
|---|---|---|
| 드론 2대 → 3대 | ingest 워커, detect-worker | 복원 주기·자원 그대로 |
| 복원 15초 초과 | recon-worker를 V100 전용으로 격리, detect-worker를 T4로 이전 | 제어 평면·배포 그대로 |
| 시청 단말 급증 | edge-serving 복제 (다중 PoP) | Core 파이프라인 무관 |
| 탐지 모델 교체 | detect-worker만 재배포 | 복원 무중단 |

## 5. 구간별 제약과 해소

경로 전체를 네 구간으로 끊고 각각의 실제 제약을 따졌다. **실질적인 병목은 두 곳뿐이고, 둘 다 해소 방법이 확정돼 있다.** 나머지 둘은 병목처럼 보였을 뿐 수치를 확인하면 여유가 있다.

| 구간 | 필요 | 가용 | 판정 | 해소 수단 |
|---|---|---|---|---|
| 드론 → 게이트웨이 | 원본 영상 | 제조사 무선링크 | 여유 | 로컬 무선, 대역 아닌 거리 제약 |
| 게이트웨이 → KOREN | 15–33 Mbps | 20–60 Mbps | 빠듯 | 적응 인코딩 · 4K 로컬 녹화 |
| KOREN 내부 | 30MB 버스트 | 10G 이상 백본 | 여유 | 대체 불가능한 구간 |
| 브리지 → 단말 | 30MB × N | 브리지 업로드 | 초과 위험 | **.spz 전환 (10배 압축)** |

### 병목 1 · 드론 → 현장 게이트웨이 — 병목 아님

제조사 무선링크(OcuSync 등)로 원본 영상이 게이트웨이 노트북에 들어온다. 이 구간은 로컬 무선이라 대역이 넉넉하고, 우리가 바꿀 수 있는 부분도 아니다. 실제 제약은 대역이 아니라 거리와 가시선이다. 수 km 범위를 벗어나면 링크가 끊긴다. 드론에 LTE 인코더를 직접 탑재하면 해결되지만 대당 수백만 원이라 MVP 범위 밖이며, 재난 현장 가정상 게이트웨이를 현장 인근에 두는 운용으로 충분하다.

> **판정**: 대역 문제 없음 — 운용 반경으로 관리

### 병목 2 · 게이트웨이 → KOREN 진입(상용 5G 업링크) — 해소됨·전제 정정

가장 많이 지적받는 구간이고, **초기 산정이 틀렸던 곳**이다. 제안서에는 "드론 1대당 50~100 Mbps, 3대 수백 Mbps 동시 전송"으로 적혀 있었으나, 이는 준무압축이나 4K60 고비트레이트를 가정할 때의 값이다. H.265 실시간 인코딩 기준으로 다시 계산하면 한 자릿수로 떨어진다.

| 조건 | 3대 합계 | 상용 5G(20~60Mbps) 대비 |
|---|---|---|
| 초기 산정(근거 없음) | 150–300 Mbps | 불가 |
| 4K30 실시간 | 48–84 Mbps | 셀 상태 나쁘면 불가 |
| **1080p30 실시간 (채택)** | **15–33 Mbps** | **성립** |

복원 입력이 긴 변 1600px라 1080p로 품질 손실이 없다.

**해소 방법**
1. **적응 인코딩** — 게이트웨이가 링크 상태를 보고 4K↔1080p를 자동 조절. 화질을 희생해 끊김을 막는다.
2. **4K 원본은 로컬 녹화** — 버리지 않고 게이트웨이 저장소에 남겨, 상황 종료 후 고품질 재복원에 쓴다. 실시간과 정밀 분석의 용도를 분리하는 것이지 타협이 아니다.
3. **병목 자체를 측정값으로 활용** — 이 구간은 실험군·대조군 공통이므로, 여기서 나오는 손실·지연 통계가 대조 실험의 기준선이 된다.

> **발표에서 반드시 정정할 문장**: KOREN은 이 구간을 가속하지 못한다. 인제스트 총량은 상용 5G가 결정하고, 그 뒤가 40G든 7T든 총량은 늘지 않는다. "고해상도 영상을 10Gbps 고속망으로 전송"이라는 표현은 액세스망 병목 지적에 그대로 무너진다.

> **판정**: 1080p 운용으로 성립 — 추가 비용 0, 구현 변경 0

### 병목 3 · KOREN 내부 — 대전 ↔ 판교 — 대체 불가능한 구간

여기가 **KOREN이 실제로 값을 하는 유일한 구간**이다. 30초마다 프레임 묶음이 판교로 가고 복원 결과가 대전으로 돌아온다. 장면 1회분이 30MB일 때 링크 대역별 전송 시간:

| 링크 | 30MB 전송 | 판정 |
|---|---|---|
| 100 Mbps (일반 회선) | 2.4 s | 30초 예산의 8%를 배포에만 소모 |
| 1 Gbps | 240 ms | "수백 ms 이내" 충족 |
| 10 Gbps (KOREN 백본) | 24 ms | 여유 |

이것은 30초마다 터지는 **버스트**라 평균 대역(약 8 Mbps)이 아니라 순간 대역이 지배한다. 상용 인터넷 경로에서는 여기에 경합과 TCP slow start가 얹혀 실측이 더 나빠진다.

> **정정된 주장**: 10Gbps급 전용망이 필요한 대상은 드론 영상이 아니라 **3D 모델 배포**다. "Core↔Edge 3D 모델 전송 저지연은 전용망만 충족"이라는 문장은 정확하며, 대상만 바꾸면 그대로 유효하다.

추가 여유: VM 카탈로그에 56G InfiniBand 옵션이 있어, 프레임·모델 왕복이 부담이 되면 신청으로 해결할 수 있다(단, §10 출처 검증에서 "재구성" 등급 — 확인 필요).

> **판정**: 여유 — 이 구간이 KOREN 활용의 핵심 근거

### 병목 4 · 브리지 → 사용자 단말(배포) — 실질 병목·해소 확정

두 문제가 겹쳐 있어 진단이 헷갈리기 쉽다.

**첫째, 접속 정책**: KOREN이 폐쇄망이라 사용자 단말이 망 안의 서버에 붙을 수 없다. 대역 문제가 아니라 원천적 차단이며, 배포 지점을 망외 브리지로 내리는 것으로 해결된다.

**둘째, 진짜 대역 병목**: 브리지에서 나가는 업로드 한 파이프에 영상 릴레이(상시)와 복원본 배포(버스트)가 함께 올라탄다. 가정용·소규모 회선은 업로드가 좁아 여기서 예산을 초과한다.

| 파일·업로드 조건 | 동시 3대 소요 | 판정 |
|---|---|---|
| .ply 30MB×3, 업로드 100Mbps | 11.0s | 초과 |
| .ply 30MB×3, 업로드 500Mbps | 1.5s | 통과(회선 좋을 때만) |
| **.spz 4MB×3, 업로드 100Mbps** | **1.2s** | **통과** |
| .spz 4MB×3, 업로드 500Mbps | 0.2s | 여유 |

핵심은 회선을 키우는 게 아니라 보내는 양을 줄이는 것. `.spz` 전환으로 업로드 실측값이 무엇이든 예산 안으로 들어온다.

**해소 방법 — 3단계**
1. **.spz 전환 (필수)** — 30MB → 3–5MB. 뷰어가 이미 해당 렌더러를 쓰고 있어 클라이언트 대응 부담이 작다. 업로드 실측값과 무관하게 예산을 확보하는 유일한 수단.
2. **동시 접속 통제 (데모)** — 발표 시연은 상황판과 대원 뷰어 두 화면이면 충분.
3. **CDN 확장 (다수 서빙 시)** — Core가 아웃바운드로 클라우드 오브젝트 스토리지에 올리고 CDN이 배포하면 브리지 업로드에서 서빙 트래픽이 통째로 빠진다. 대조군 인프라와 계정을 공유할 수 있다.

마지막 홉이 상용망인 것은 정상 설계다. 어떤 CDN도 백본은 전용망이고 마지막 마일은 ISP를 탄다.

> **판정**: .spz 전환으로 해소 — 선행 착수 항목

## 6. 배포 매핑

서비스를 어느 자원에 올릴지는 취향이 아니라 자원 요구가 정한다. GPU가 필요한 것만 판교로 보내고, 나머지는 제어 노드와 브리지에 나눈다.

| 서비스 | 배치 | 자원 요구 | 배치 근거 |
|---|---|---|---|
| gw-encoder | 현장 노트북 | CPU·인코딩 | 드론 무선링크가 닿는 곳에 있어야 함 |
| gw-pose | 현장 노트북 | 경량 | 영상과 같은 시계를 써야 타임스탬프가 맞음 |
| gw-cache | 현장 노트북 | 스토리지 | 4K 원본 녹화 + 백홀 단절 시 로컬 서빙 |
| bridge-relay | 브리지 | I/O | 등록 IP를 가진 유일한 지점 |
| edge-serving | 브리지 | 업로드 대역 | KOREN 안에서는 유동 IP 단말을 못 받음 |
| asset-cache | 브리지 | 스토리지 | 단말 요청이 KOREN까지 가지 않게 차단 |
| ingest | 대전 VM | I/O·네트워크 | GPU 불필요, 스트림 수신 전담 |
| segmenter | 대전 VM | CPU·메모리 | 프레임 버퍼링, GPU 불필요 |
| pose-sync | 대전 VM | 경량 | segmenter와 같은 메모리 공간이 유리 |
| orchestrator | 대전 VM | 경량 | 잡 발행만, 실행은 판교 |
| queue | 대전 VM | 메모리 | 제어 평면 중앙 |
| metrics | 대전 VM | 경량 | 수신측 통계가 여기 모임 |
| recon-worker | 판교 HPC | GPU 메모리 집약 | V100 16GB 전용 점유 |
| detect-worker | 판교 HPC | GPU 처리량 | T4 분리 배치도 가능 — 복원과 GPU 경합 회피 |
| project | 판교 HPC | GPU·근접성 | 복원 결과를 깊이 참조로 쓰므로 같은 노드 |
| asset-store | 판교 HPC | 스토리지 | 산출물 생성 지점 |

**확장 여지**: `detect-worker`를 T4 노드로 분리하면 복원과 탐지가 GPU를 두고 경쟁하지 않는다. 복원 잡이 15초를 못 맞출 때 V100을 복원 전용으로 비우는 첫 번째 카드다. 카탈로그에 vGPU T4 4GB 옵션이 있으므로 추가 신청으로 확보할 수 있다.

## 7. 대조 실험 토폴로지

과제의 평가 축은 "KOREN을 써서 무엇이 나아졌는가"다. 그러려면 **같은 코드가 두 경로를 타야** 하고, 두 경로의 차이가 백본과 연산 자원에만 있어야 한다. 액세스 구간을 공통으로 묶는 것이 실험 설계의 핵심이다.

```
                         [공통 구간 — 양 군 동일]
드론×3 + 게이트웨이(H.265 1080p) → 상용 5G(15–33Mbps) → 브리지(분기점)
                                                              │
                    ┌─────────────────────────────────────────┤
                    ▼ [실험군 — KOREN 전용망]         [대조군 — 일반 인터넷] ▼
              대전 VM(제어) ⇄ 판교 HPC(V100)         클라우드 VM+GPU(동일 파이프라인)
                    │      백본 10G 이상                    │  일반 인터넷 경유
                    └─────────────┬──────────────────────────┘
                                  ▼
                             단말 (동일 뷰어)

계측점:  M1 GW 송수신(공통 구간 출구) · M2 대전 VM(복원 소요) · M3 브리지(모델 배포 지연) · M4 단말(E2E·TTFV)
```

### 7.1 계측 지점

| 계측 | 측정 지점 | 지표 | 수집 방법 |
|---|---|---|---|
| M1 | GW 송신 ↔ 수신측 | 손실률·RTT·재전송 | SRT 통계 API, 경로별 동시 수집 |
| M2 | 오케스트레이터 잡 로그 | 복원·추론 소요 | 잡 시작/종료 이벤트 |
| M3 | 산출물 생성 ↔ 브리지 도착 | 모델 배포 지연 | 버전 타임스탬프 차 |
| M4 | 단말 브라우저 | E2E 지연·TTFV | 프레임 타임코드 전파 + Navigation Timing |

> **설계상 주의**: 대조군을 "같은 KOREN VM에 일반 인터넷으로 접속"으로 잡으면 성립하지 않는다. 폐쇄망이라 등록 IP 외에는 애초에 닿지 못하기 때문이다. **대조군은 상용 클라우드에 동일 파이프라인을 별도 배포하는 방식**이어야 하고, 이것이 서비스 경계를 배포 경계와 일치시켜야 하는 실질적 이유다.

## 8. 포트 맵

방화벽 신청과 도면 라벨에 그대로 쓰는 표다. 미디어 경로만 UDP이고 나머지는 전부 443으로 수렴한다.

| 구간 | 프로토콜 | 포트 | 비고 |
|---|---|---|---|
| 드론 → GW | 제조사 링크/RTSP | — | 로컬 무선 |
| GW → 브리지 → Core (영상) | SRT | UDP 8890 | 유일한 UDP 구간. 불허 시 RTSP/TCP 대체 |
| GW → 브리지 → Core (포즈·관제) | WSS | TCP 443 | MAVLink 페이로드 |
| 브리지 → Core (관리) | SSH | TCP 22 | 신청 완료 |
| Core 내부 (대전↔판교) | 내부 API/큐 | 내부 | KOREN 백본 |
| Core → 브리지 (산출물) | HTTPS 또는 rsync/SSH | TCP 443/22 | Plan A/B 양방향 가능 |
| 브리지 → 단말 (뷰어·파일) | HTTPS | TCP 443 | Range 요청 지원 |
| 브리지 → 단말 (마커) | WSS | TCP 443 | 발견 즉시 push |
| GW → 단말 (폴백) | HTTP/WS | 로컬 | WiFi AP, 백홀 단절 시 |

## 9. 최종 점검 — 놓친 것들

설계를 한 바퀴 돌려 감사한 결과다. KOREN 자원 중 안 쓰고 있던 것, 전송 계층에서 빠진 엔지니어링, 그리고 측정 자체를 무의미하게 만들 수 있는 구멍 하나가 나왔다.

### A. KOREN 기술지원 목록 — 아직 안 쓰는 것

KOREN은 회선만 주는 것이 아니라 네트워크 기능 단위로 기술지원을 한다. 지원 목록: `IPv6 · MPLS · QoS · Multicast · Ethernet-based Light-Path · 양자암호통신` + 회선 개통·증설, 컨설팅, 시험검증.

| 기능 | 활용 방식 | 효과 | 우선도 |
|---|---|---|---|
| **Multicast** | 다중 PoP Edge에 복원본을 1회 전송으로 동시 복제 | 배포 트래픽이 Edge 수와 무관해짐 | 높음 |
| QoS | SRT 영상에 DSCP EF 마킹, 벌크 전송은 BE | 전용회선 없이도 우선순위 확보 | 높음 |
| IPv6 | GW·Core에 글로벌 IPv6 할당 | CGNAT 회피 — 등록 IP 문제의 다른 해법 | 확인 필요 |
| MPLS | 트래픽 엔지니어링 경로 지정 | L2 전용회선의 대안·보완 | 중간 |
| Light-Path | 이더넷 기반 광 경로 | λ 전용회선의 실제 제공 형태 | 중간 |
| **공개시험센터(대전)** | 충남대 인근 거점에서 실증 | 판교까지 안 가도 되는 시험 환경 | 높음 |
| 컨설팅·시험검증 | 구성 설계 자문 요청 | 전용회선 설계를 NOC와 함께 | 높음 |

**멀티캐스트가 왜 큰 카드인가**: 상용 인터넷에서는 ISP가 멀티캐스트를 사실상 차단하기 때문에 쓸 수 없다. 연구망에서만 가능한 기능이고, 우리 배포 구조와 정확히 맞물린다 — 같은 `.spz`를 여러 Edge에 뿌리는 작업이 1회 전송으로 끝난다. Edge를 N개로 늘려도 유니캐스트는 원본 대역이 N배로 늘지만, 멀티캐스트는 원본 대역이 그대로 유지된다. 단, 최종 단말은 상용 5G 뒤에 있어 멀티캐스트가 안 닿는다. 적용 구간은 **Core → 다중 PoP Edge**이며, 이것이 다중 PoP 확장의 실질적 근거가 된다.

### B. 전송 계층 — 빠져 있던 엔지니어링

"10G 백본이니 빠르다"는 자동으로 성립하지 않는다. 고대역·장거리 링크는 튜닝 없이는 대역을 다 쓰지 못한다.

| 항목 | 문제 | 조치 |
|---|---|---|
| 대역폭·지연 곱(BDP) | 단일 TCP 스트림으로는 고대역 링크를 채우지 못한다 | tcp_rmem/wmem 상향, 병렬 스트림, BBR 혼잡제어 |
| MTU·점보 프레임 | 1500B로 30MB 보내면 패킷 2만 개. 9000B면 1/6 | KOREN 구간 점보 프레임 지원 여부 확인 |
| 경로 MTU 탐색 | SRT는 UDP라 프래그먼트되면 손실 증폭 | SRT payload를 경로 MTU 이하로 고정 |
| SRT 파라미터 | "SRT 쓴다"까지만 정해짐, 설정값 없음 | latency ≈ RTT×4, maxbw, oheadbw 산정 |
| 버퍼블로트 | 상용 5G 업링크 고질 문제 | 송신측 페이싱, SRT latency를 실측 RTT로 조정 |
| 혼잡 제어 | CUBIC은 장거리 고대역에서 회복 느림 | BBR 적용 후 전후 비교 |

이 항목들은 튜닝 전후를 실측해 그래프로 보여줄 수 있다. "10G를 받았다"보다 "10G를 실제로 쓰기 위해 무엇을 했다"가 훨씬 강한 서사다.

### C. 계측 정확도 — 가장 위험한 구멍

> **측정하려는 값보다 측정 오차가 클 수 있다.** E2E 지연 목표는 수백 ms 단위인데, 현재 설계에는 노드 간 시간 동기가 NTP로만 되어 있다. 일반적인 NTP 동기 오차는 수 ms~수십 ms로, 측정하려는 구간 지연과 같은 자릿수다. **이 상태로는 "KOREN이 몇 ms 빠르다"를 주장할 수 없다.**

조치는 셋 중 하나:
1. 게이트웨이의 GPS 시각을 기준으로 삼고 Core 노드를 그에 맞춘다.
2. KOREN 구간에 PTP 적용 가능 여부를 확인한다.
3. **절대 시각 대신 왕복 측정으로 설계를 바꿔 단일 시계만 쓴다** (가장 현실적). 같은 노드에서 보내고 받아 RTT를 재면 시계 동기가 아예 필요 없다. 다만 편도 지연의 비대칭은 못 잡으므로, 지표 정의를 왕복 기준으로 다시 쓰는 작업이 선행돼야 한다.

### D. 실험 설계 보완

| 항목 | 현재 | 보완 |
|---|---|---|
| 대조군 GPU | "상용 클라우드 GPU" | **V100 동급으로 고정.** 다르면 연산 시간 차이가 네트워크 차이로 오인된다 |
| 측정 반복 | 정의 없음 | 구간별 최소 반복 횟수와 분포 보고(중앙값·p95) 규정 |
| 측정 시간대 | 정의 없음 | 상용 5G는 시간대별 혼잡이 다르므로 양 군 동시 측정 |
| 기준선 | 없음 | 튜닝 전 값을 먼저 확보해야 개선 폭을 주장할 수 있다 |
| 공통 구간 검증 | 가정 | M1에서 양 군의 액세스 품질이 실제로 같았는지 사후 확인 |

### E. 운영 시나리오

| 장애 | 시스템 동작 | 현재 준비 |
|---|---|---|
| 5G 백홀 단절 | GW WiFi AP로 로컬 서빙 전환 | 설계됨 |
| KOREN 진입 실패 | GW 로컬 녹화만 지속, 복구 후 일괄 처리 | 정의 필요 |
| 복원 워커 장애 | 이전 버전 장면 유지, 탐지는 계속 | 설계됨 |
| 탐지 워커 장애 | 복원만 계속, 마커 갱신 중단 | 설계됨 |
| **브리지 장애** | **전체 중단 — 단일 장애점** | **폴백 미정의** |
| 드론 링크 상실 | 남은 드론으로 부분 복원 지속 | 정의 필요 |

> **단일 장애점**: 브리지가 죽으면 전부 멈춘다. 관문과 배포를 한 노드가 겸하는 구조의 대가다. 등록 IP를 두 곳(자택·충남대) 확보해 뒀으므로 이중화가 가능하며, 전환 절차를 정의해 두는 것이 남은 작업이다.

### F. 시연 대비

발표 당일 드론을 띄우지 못하는 상황(실내·기상·규제)에 대비해 **사전 녹화 스트림을 실시간처럼 재생하는 모드**가 필요하다. 파이프라인 입력이 SRT 스트림이므로, 녹화 파일을 같은 프로토콜로 흘려보내면 이후 경로는 완전히 동일하다. 서비스 경계가 명확한 덕에 입력단만 바꾸면 되는 구조이며, 이 역시 MSA 분해의 부수 효과다.

## 11. 30초 예산과 남은 리스크

구간별 해소를 반영해 예산을 다시 배분하면 다음과 같다. 네트워크 항목은 모두 여유가 있고, **전체 성립 여부는 복원 잡 하나에 걸려 있다.**

| 단계 | 예산 | 근거·상태 |
|---|---|---|
| 드론 → Core 업링크 | 1–2 s | SRT latency 200–500ms + 인코딩 |
| 세그먼트 확정 대기 | ~10 s | 10초 분량 프레임으로 잡 1회 구성 |
| **3DGS 증분 복원 1회** | **10–15 s** | V100 실측 필요 — 유일한 미검증 항목 |
| Core → 브리지 전달 | < 1 s | KOREN 백본, 방향 무관 |
| 브리지 → 단말 (TTFV) | 1–3 s | .spz 전환 전제 |
| **합계** | **≈ 23–31 s** | 이후 주기부터 파이프라인이 겹쳐 30초마다 갱신 |

> **최대 리스크**: V100에서 증분 복원 1회가 15초 안에 끝나는가. 배정 GPU가 H200이 아닌 V100으로 확정됐고, 로컬 실측은 학습만 3.2분이었다. iteration을 줄여 15초에 맞추되 품질이 유지되는 지점을 찾아야 한다. 측정 설계는 iteration sweep(500/1000/2000/5000/30000)으로 wall-clock과 PSNR을 함께 기록하는 것이다. 이 숫자가 미달이면 30초 주기라는 과제 정의 자체를 조정해야 하므로, 발표 자료 확정보다 먼저 나와야 한다. 현재 복원 파이프라인은 인터페이스 스캐폴드 상태라 gsplat 툴체인 구축이 선행된다.

### 실행 순서

1. **복원 실측** — 크리티컬 패스. 다른 모든 수치가 여기에 의존한다.
2. **.spz 전환** — 병목 4 해소. 실측 대기 없이 착수 가능.
3. **발표 자료 대역폭 주장 교체** — 병목 2의 정정 내용 반영.
4. **KOREN VM 배정 확인** — 2노드 구성이 맞는지 NOC에 확인 (2026-08-15 기준 SSH로 확정됨, 판교 접근 경로만 미해결).
5. **지식지원 신청 (L2 전용회선)** — 신청서 2번 항목에 `전용회선(L2)` 체크.
6. **외부 SSH 개통** — 대전 완료. 판교(HPC 포털 VM)는 NOC 회신 대기 중.

### 미확정 항목

| 항목 | 영향 | 확인 방법 |
|---|---|---|
| V100 복원 1회 소요 | 30초 주기 성립 여부 전체 | iteration sweep 실측 |
| KOREN VM 별도 배정 여부 | 2노드 구성·백본 활용 근거 | ✅ 해결 (SSH 실측 확정) |
| UDP 8890 개방 | SRT 사용 가부 (대체안 있음) | 방화벽 신청 회신 |
| 브리지 업로드 실효 대역 | .spz 전환 시 영향 소멸 | speedtest |
| 판교(HPC 포털 VM) 외부 SSH | 개발 편의 (콘솔로 대체 가능) | NOC 재문의 발송, 회신 대기 |
